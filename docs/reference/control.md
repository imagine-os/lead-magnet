# Control model: actions -> WebMCP tools -> CLI -> voice

_T45 (WebMCP), T46 (voice controller + command palette) and T47 (spatial navigation), 2026-09-19, Fable 5.1. Binding principles: P-04, P-05. Related: `surfaces.md` §1.3 / §1.6 / §2.2a, `docs/pages/D-04.md`, `docs/pages/HUB-01.md`, `docs/qa/dpad-report.md`._

One page declares its actions once; everything that can drive the product reads that one declaration.

```
PageSpec.actions (ActionDef: id, label, intent, permission?, params?)      <- the page's buttons, menu items, form submits
   |  useActions(code, { id: handler })  while the page is mounted           <- the actions bus, src/actions/index.ts
   v
window.__leadmagnet.routes[].spec.actions                                    <- the manifest (D-01, D-04)
   |  src/actions/webmcp.ts  syncTools()  one tool per unique action id
   v
window.__leadmagnet.tools[]  +  window.__leadmagnet.runAction(id, params)    <- always present (Playwright, CLI, voice)
navigator.modelContext.registerTool(tool)                                    <- when the browser has WebMCP (feature-detected)
   |
   +-- npm run actions -- list | export | run <id>                            <- the CLI, scripts/actions.mjs
   +-- docs/reference/actions-manifest.json, voice-vocabulary.json          <- static exports of the same data
   +-- CommandPalette (T46): typed or spoken phrase -> matchPhrase over the same vocabulary -> runAction(action, slots)
   |     Ctrl/Cmd+K on every shell, "Commands" in the TopBar and on the hub, hub.openCommands / hub.voiceListen
   +-- remote / gamepad d-pad (T47): moves focus between the same buttons, Enter activates them (hub, demo, DesktopShell, landing)
```

## 1. Declaring actions (what a page author does)
Nothing new. Every button, menu item and form submit on a page is an `ActionDef` in its `PageSpec.actions` (`id: '<module>.<verb>'`, `label`, `intent` = the phrase a person would say with `{slots}`, `permission?` = the string the page calls `can()` with, `params?` = `string | number | id | date | enum:a|b`). While mounted the page calls `useActions(code, { '<id>': handler })`; handlers take ids, never screen positions, and return something readable (an object; `{ ok, id, status }` is the house shape). That is the whole contract: the tool, the CLI verb, the voice phrase and the D-04 row are generated from it. A button without an entry is incomplete; removing a button removes its entry in the same commit (P-05).

## 2. WebMCP tools (`src/actions/webmcp.ts`)
- **One tool per unique action id.** `name = id`, `description = "<intent> — "<label>" on <codes> (needs <permission> | any role)"`, `inputSchema` = JSON Schema built from `params` (`string`/`id` -> string, `number` -> number, `date` -> string `format: date-time`, `enum:a|b` -> string enum; every slot optional because handlers default what the speaker left out; `additionalProperties: false`). An id declared by several pages (`booking.openDemo`, `demo.goto`, ...) is one tool with several `hosts`.
- **`execute(params)`** does, in order: (a) `can(permission)` for the current session (`"plan.setStatus" needs plan.edit; the current role (guest) does not have it`); (b) validate `params` against the schema; (c) if no handler is live, pick a host page the role may open (parameterless path first, then one whose params the call supplies), fill `:slug` / `:prospectId` / `:id` / `:role` / `:table` / `:code` from `params` or the first seeded row (`pages[0].slug`, `prospects[0].id`, `tasks[0].id` under `/plan`), navigate, and wait up to 4 s for the page to register; (d) `run(id, params)` and return `{ ok, message, data?, deduped? }` - `message` is a sentence, `data` is the handler's return value.
- **Registration.** At app start and whenever the live handler set changes (`onActionsChange`), `ControlBridge` (mounted once in `App.tsx` inside the router) calls `syncTools(manifest)`: tools are rebuilt, `live` refreshed, and registered with `navigator.modelContext.registerTool` when that function exists - once per name (the proposal throws on duplicates), with `annotations: { pages, permission, label }` and an `execute` that wraps the result as `{ content: [{ type: 'text', text }], structuredContent }`. No API present -> nothing is registered and nothing breaks: `window.__leadmagnet.tools`, `.vocabulary`, `.runAction()` and `.webmcp` (`{ available, registered: 'navigator' | 'window', count, live, updatedAt }`) are always published. `provideContext` / `clearContext` are deliberately not used (they clear other scripts' tools and were dropped from the 2026 revision of the proposal).
- **Idempotency rule.** Handlers may be non-idempotent (a status write, a booking insert). The surface guards them: an identical `(id, stableHash(params))` within **1.5 s** returns the first call's result with `deduped: true` instead of running the handler again (a double-tap on a remote, a repeated voice phrase, an agent retry). Two calls with different params, or the same call after the window, both run. Handlers should still be written idempotently where the data allows (set a status, do not toggle it); the guard is the safety net, not the design.
- **Bridge.** `installControlBridge({ can, role, navigate, currentPath, resolveParam, canOpen })` is what the React tree lends the bus; nothing in `src/actions` imports React context directly, so the same surface can run under a different shell later.

## 3. CLI (`npm run actions -- <command>`, `scripts/actions.mjs`)
| Command | What | Notes |
| --- | --- | --- |
| `list [--page CODE] [--json]` | every tool: id, pages, permission, intent, params | built from the compiled specs (esbuild bundles `src/modules/*/index.ts`, built beats stub like the registry); no browser |
| `export` | writes `docs/reference/actions-manifest.json` (tools with schemas and hosts) and `docs/reference/voice-vocabulary.json` (phrase -> action with slots) | run after any action change; commit both |
| `run <action.id> [--param k=v ...] [--as <role>] [--port N] [--json]` | Playwright: serves `dist/` on 4173 (or reuses whatever answers on `--port`, e.g. a `vite` dev server), opens the hub as `<role>` (`super_admin` default), calls `window.__leadmagnet.runAction(id, params)`, prints the result and the route it ended on, exits 1 on `ok: false` | Chromium from `/opt/pw-browsers`; external requests blocked |

Examples that were run headless on 2026-09-19: `npm run actions -- list` (119 tools / 179 declared rows / 51 routes), `npm run actions -- run plan.setStatus --param task=T45 --param status=doing --port=5199` -> `ok · ran plan.setStatus (opened K-04 /plan/tasks/T45) · data {"ok":true,"id":"T45","status":"doing"}`, then the same with `status=backlog` to revert. Each CLI run is a fresh browser context, so the mock database it writes is that context's localStorage; against Supabase (T44) the write is real.

From Playwright or the browser console the entry point is the same: `await window.__leadmagnet.runAction('demo.goto', { section: 'money' })` navigates to C-01 for the first prospect and switches the section.

## 4. Voice controller and command palette (T46)
The vocabulary (`docs/reference/voice-vocabulary.json` = `window.__leadmagnet.vocabulary`, `[{ phrase, action, slots, pages, permission }]` straight from `intent` and `params`) now has its listener and matcher. Three layers, each usable alone:

- **`matchPhrase(phrase, vocabulary, { lang?, page?, route?, live?, limit?, threshold? }) => Match[]`** (`src/a11y/voice.ts`, pure, `npm run test:voice`). Pipeline: normalise (lowercase, accents and punctuation off, ids like `T45` / `pro_maya` kept) -> multi-word rewrites (`modo oscuro` -> `dark mode`, `go to` -> `open`, `turn on` -> `on`, ...) -> per-token canon (ES -> EN dictionary of ~400 forms incl. conjugations, EN synonyms `show / view / see / list`, light stem) -> **align** the intent template in order (literal tokens must appear in order, stopwords are free, the tokens between two literals fill the slot declared between them) -> **typed slot extraction** (`number`: digits or number words EN / ES; `enum`: a value or its ES word, `hecha` -> `done`; `id`: an id-shaped token, else an id in the current `route` when the speaker says "this / esta" or gives none; `string`: a quoted span first, else the aligned words) -> **score** `0.55 coverage + 0.15 precision + 0.15 bigram similarity + 0.15 slot fill (+0.15 on the current page, +0.05 live)`; below `threshold` (0.45) is dropped. `Match = { action, score, params, missing, sources, phraseFilled, onPage, live, coverage }`. Same phrase on two pages (`reset the demo database` on HUB-01 and D-03) is a tie the `page` option breaks. `fillPhrase(intent, params)` renders the phrase back.
- **`useVoice({ lang, onResult, onError }) => { state, supported, start, stop, transcript, error }`** (`src/a11y/useVoice.ts`). `SpeechRecognition` / `webkitSpeechRecognition` feature-detected (`voiceSupported()`); states `idle | listening | unsupported | denied`; `start()` returns `false` and does nothing without transient user activation (`navigator.userActivation.isActive`), when unsupported, denied or already listening; one utterance per start, interim results on, `lang` -> `en-US` / `es-US`. **Nothing starts listening on mount or on state change** (never auto-listen).
- **`CommandPalette`** (`src/components/organism/CommandPalette/`, mounted once by `ControlBridge`, so it exists on every shell including landing and demo pages). Opened by **Ctrl/Cmd+K**, the TopBar **Commands** button (every DesktopShell page), the hub's **Commands** and **Speak** buttons, and the actions `hub.openCommands` / `hub.voiceListen` (`openPalette({ query?, voice? })` in `src/actions/palette.ts` is the store behind all of them). Empty query = the actions live on the current page; a typed or spoken phrase = ranked matches (label, phrase with slots filled, page badge, live / opens-page, permission), **role-gated with `can(permission)`** (hidden ones are counted: "n more need another role"). Up / Down choose, Enter or click runs through `runAction`; a match with slots shows a params form generated from the tool's JSON Schema (`Select` for enums, `Input` otherwise), prefilled from the phrase. Success = toast with the tool's `message` + close; failure = the message inline. Voice: the **Speak** button starts `useVoice`; a final transcript with score >= 0.8, every slot filled and 0.15 ahead of the runner-up runs at once, anything less lists the matches under "Heard: ...". Unsupported browser -> the mic is a `Placeholder` ("voice not supported in this browser", P-09); denied -> the status line says so and the button is disabled. `hub.voiceListen` called from the bus / CLI (no gesture) opens the palette and focuses the mic instead of listening.

Strings: `control.*` in `src/modules/hub/index.ts` (D-092: every string lives in a module table; the hub declares the palette's actions). Checked headless on 2026-09-19 (dev server, Chromium): Ctrl+K opens, empty query lists 8 live hub actions, "switch to dark mode" -> Theme -> Enter toggled the theme, closed and toasted; "set T45 to doing" prefilled `task = T45`, `status = doing`; `runAction('hub.voiceListen')` opened the palette without listening; TopBar Commands opens it on `/studio`; zero page errors.

## 5. Remote / gamepad d-pad (T47, `src/a11y`)
- `useSpatialNav(ref, { enabled?, onBack? }) => { move, activate, back, rootRef }` on a container: arrow keys move focus to the nearest focusable element in that direction (distance along the axis + twice the orthogonal gap; same row / column wins; **no wrap** - an edge stays put), Enter / Space activate custom focusables (native buttons and links keep their native activation; Space on a link clicks it), Backspace / Escape go one hash level up (`/demo/x/comms` -> `/demo/x`; `onBack` overrides). It is active only while focus is inside the container or nothing is focused, and never for an arrow the focused control owns: all four inside `select`, `textarea`, `contenteditable`, sliders / combos / grids, iframes and anything under `[data-spatial="skip"]`; **Left / Right only** inside a single-line text field, a tablist or a radiogroup (`Tabs`, `SegmentedControl`: Up / Down leave them, so they are never a trap); **Up / Down only** inside a listbox / menu / tree. Never while a modal dialog is actually open (a closed `<dialog>` in the DOM, as `Modal` keeps one, does not count). **Escape inside a select or text field parks focus** (blur) and the next arrow continues from that spot: a remote has no Tab to leave a control. Tab order is untouched.
- `useGamepadNav(controls, enabled?)`: d-pad (buttons 12-15) and left stick (dead zone 0.6, repeat 220 ms) -> `move`, A (0) -> `activate`, B (1) -> `back`; polls `navigator.getGamepads()` on animation frames only while a gamepad is connected and the document has focus; no Gamepad API -> no listeners.
- **Where it is mounted:** HUB-01 (`HubPage.tsx`), the demo shell (`DemoShell.tsx`, C-01..C-07), **`DesktopShell` root** (studio / admin / plan / dev / docs / manual: sidebar, top bar and content are one focus grid, so Left from the content reaches the sidebar; Escape / Backspace close the drawer under 900 px, else go one hash level up), and the landing pages (`LandingPage.tsx`, landing worker). The exact call on a page root: `const root = useRef<HTMLDivElement>(null); const spatial = useSpatialNav(root, { onBack? }); useGamepadNav(spatial);` then `ref={root}` on the element. The hub footer shows a bilingual "TV mode" hint at >= 1920 (`useViewportAtLeast(1920)`, `hub.tv_hint`).
- Regions that own their arrows carry `data-spatial="skip"`: K-03 graph (`.pl-graph-scroll`), the CommandPalette body, and (requested) the D-07 canvas `.cv-view` and the landing RoleViews strip. `Tabs` (tablist) and `SegmentedControl` (radiogroup) are excluded by role already.
- **Rehearsal:** `npm run qa:dpad [-- --only=/studio --codes=K-01 --width=1920 --port=N --server=dev|preview|auto --max-steps=400 --strict]` walks every built route at 1920 with arrow keys only (breadth-first from nothing focused) and writes `docs/qa/dpad-report.{md,json}`: reachable / candidates, primary CTAs never reached, dead ends (real traps) vs arrow-owning controls met, Backspace behaviour, routes without the hook. Report only (exit 0) unless `--strict`.

## 6. Adding a page or an action: the checklist
1. Add the `ActionDef` to the spec and the handler to `useActions`; run `npm run typecheck`.
2. `npm run actions -- list --page <CODE>` shows the tool; `npm run actions -- export` refreshes the two JSON files (commit them).
3. Open `/#/dev/actions` (D-04): the row shows "live" on its page, "opens page" elsewhere; "Run" opens the params form generated from the schema and shows the voice phrase and the JSON Schema.
4. `surfaces.md` §1.4 counts and this file's examples if the shape changed (P-10).
5. Say the phrase: Ctrl/Cmd+K, type or speak the `intent` with real slot values; the top match must be your action. If a synonym people would use is missing, add it to `DICT` / `PHRASES` in `src/a11y/voice.ts` with a check in `scripts/test-voice.mjs` (`npm run test:voice`).
6. If the page owns arrow keys anywhere, mark that region `data-spatial="skip"`; `npm run qa:dpad -- --codes=<CODE>` shows what a remote can reach.
