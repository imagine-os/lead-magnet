# 0010 - Control: WebMCP surface, actions CLI, d-pad spatial navigation (T45, T47 groundwork)

version: 0.3.0
date: 2026-09-19
prompt: 0003
intent: Make the actions manifest a real control surface: one WebMCP tool per action (registered through `navigator.modelContext` when the browser has it, always exposed on `window.__leadmagnet`), a terminal CLI over the same entry point, static JSON exports (manifest + voice vocabulary), a D-04 page that runs any action from a schema-generated form, and the P-04 groundwork: arrow-key / gamepad spatial focus on the hub and the OS demo with a TV-mode hint at >= 1920.
decision: (1) registration goes through `registerTool` only, feature-detected, once per name; `provideContext` / `clearContext` are not used (they clear other scripts' tools and were removed from the 2026 revision of the proposal); the window surface (`tools`, `runAction`, `vocabulary`, `webmcp`) is always published so Playwright, the CLI and voice never depend on the browser API (proposed D-064); (2) the surface, not each handler, guards idempotency: identical `(id, stableHash(params))` within 1.5 s returns the first result with `deduped: true` (proposed D-065); (3) `execute` opens the host page when the handler is not live, resolving route params from the call or the first seeded row, and waits up to 4 s for registration, so every one of the 119 tools is callable from the hub (proposed D-066); (4) spatial navigation is geometric (nearest in the arrow direction, no wrap), container-scoped, never inside arrow-owning controls or open dialogs, and mounted only on HUB-01 and C-01..C-07 for now (proposed D-067); (5) the React tree lends the bus `can` / `navigate` / seeded defaults through one `ControlBridge` component instead of `src/actions` importing contexts (keeps the surface shell-agnostic).
rejected: a hand-maintained tools list next to the specs (the manifest already is the list; drift would be a correctness bug under D-008); re-registering navigator tools on every handler change (the proposal throws on duplicate names and live status belongs on the window object, not in the description); wrap-around focus (on a TV grid an edge that jumps to the other side is disorienting; remotes expect an edge to stop); a `--experimental-strip-types` import of `src/modules/*/index.ts` for the CLI (those files import `.tsx` and `.css`; esbuild - already a Vite dependency - bundles them with the registry's built-beats-stub rule, while the pure `schema.ts` is still imported through type stripping); putting the TV hint strings in `hub/index.ts` (not this worker's file; `bi()` on an `{ en, es }` object is the sanctioned bilingual path, see request below); a "Show tool" button per D-04 row (would need a new action entry in `dev/specs.ts`, not this worker's file; "Run" opens the same panel).
files: src/actions/schema.ts (new, pure: paramSchema, validateParams, buildToolSpecs, buildVocabulary, intentSlots, stableHash, fillRoutePath, pickHost), src/actions/webmcp.ts (new: syncTools, runAction, getTools, webmcpStatus, installControlBridge, IDEMPOTENCY_WINDOW_MS, REGISTER_TIMEOUT_MS), src/app/ControlBridge.tsx (new), src/app/App.tsx (+ControlBridge), src/app/manifest.ts (LeadMagnetGlobal, merge on publish), src/a11y/{spatial.ts,useSpatialNav.ts,useGamepadNav.ts,useViewportAtLeast.ts,strings.ts,index.ts} (new), src/modules/hub/HubPage.tsx (useSpatialNav + useGamepadNav + TV hint), src/modules/os-demo/DemoShell.tsx (useSpatialNav + useGamepadNav), src/modules/dev/ActionsPage.tsx (rewritten), scripts/actions.mjs (new), package.json (`actions` script), docs/reference/control.md (new), docs/reference/surfaces.md, docs/reference/actions-manifest.json + voice-vocabulary.json (generated)

- `src/actions/webmcp.ts` exports `syncTools, runAction, getTools, getTool, onToolsChange, webmcpStatus, webmcpAvailable, installControlBridge`; `src/actions/schema.ts` is pure and Node-importable (strip-types).
